## Phase 8 (amended, post-Phase-7, blocking archive): fix Phase 7's own already-live migration — `rolbypassrls` on `postgres` breaks the masked view, replace it with a `SECURITY DEFINER` function

The orchestrator applied Phase 7's migration (`20260903130000`) to production, then live-tested it (rolled-back transactions, real simulated JWTs) and found its own "View Security Semantics" assumption false for this project: `postgres` (the table/view owner) has `rolbypassrls = true`. `FORCE ROW LEVEL SECURITY` does not override an explicit `BYPASSRLS` role attribute — documented Postgres behavior — so `weekly_ai_reports_for_role` returned every row to every caller, bypassing row-level filtering entirely (its column-masking `CASE` logic was itself correct). `ALTER VIEW ... SET (security_invoker = true)` was also tried and confirmed to fail differently: it requires the calling role to hold direct `SELECT` on the base table, which Phase 7's own `REVOKE` (correct, must stay) makes impossible. The orchestrator live-verified the actual fix (rolled-back transactions, 3 real scenarios): a `SECURITY DEFINER` function with the row-filter as an explicit `WHERE` clause, immune to the `BYPASSRLS` failure mode. Phase 7's migration is NOT edited (already live); a new migration replaces its view.
